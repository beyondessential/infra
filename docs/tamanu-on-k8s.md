# Tamanu on Kubernetes

This is how we run Tamanu on the `tamanu-internal-main` EKS cluster — everything from preview branches on pull requests to internal demo deployments and release candidates.

For the cluster itself see `docs/kubernetes.md`. For the Linux-server variant see `docs/tamanu-on-linux.md`.

The story uses **four Pulumi stacks** plus HNC. Once you internalise the division of labour it's straightforward.

| Stack | Scope | Purpose |
|---|---|---|
| `pulumi/tamanu/k8s-infra` | cluster-wide, one copy per cluster | Shared namespaces, RBAC, config templates, shared secrets, pgsnap operator. |
| `pulumi/tamanu/on-k8s` | one per Tamanu deployment | The deployment itself — central + N facilities + patient portal + ingress + DB. |
| `pulumi/tamanu/meta` | cluster-wide | Tamanu "meta" version/orchestration servers (`meta.tamanu.app`). |
| `pulumi/tamanu/ips-infra` + `pulumi/tamanu/ips` | cluster-wide + per-deployment | International Patient Summary S3 bucket + per-deployment IAM to write to it. |

---

## 1. `tamanu/k8s-infra` — once per cluster

Lays down the shared ground every Tamanu deployment uses.

### 1.1 Namespaces

- **`tamanu-system`** — shared configuration. Holds:
  - Cluster-wide secrets (Bugsnag, Mailgun, Tupaia credentials).
  - Per-variant **config templates** as ConfigMaps: `basic`, `pr`, `rc`, `demo`. These are Nunjucks (`.njk`) templates for the central, facility, and provisioning JSON5 configs that Tamanu needs at runtime. `tamanu-on-k8s` picks one via `configTemplate` config.
- **`tamanu-super`** — parent of every per-deployment namespace, via HNC. RoleBindings here propagate down to every child. Deployments are created as **SubnamespaceAnchors** inside it — delete the anchor and HNC cascades the whole deployment namespace away.
- **`tamanu-seed`** — isolated from the HNC hierarchy, runs the pgsnap operator and seed/bootstrap jobs.

### 1.2 RBAC (propagated via HNC)

Both ClusterRoles, bound once in `tamanu-super` and propagated by HNC into every child namespace.

- **`tamanu-deploy`** — CI / Pulumi role. Manage Secrets, ConfigMaps, Services, ServiceAccounts, Deployments, Jobs, Ingresses, Gateway API resources, CNPG Clusters, and SubnamespaceAnchors.
- **`tamanu-engineer`** — humans troubleshooting: read-only across the namespace plus `pods/log`, `pods/exec`, `pods/portforward`, pod delete (for restart-by-delete), and ConfigMap/Secret edit.

Bound via Tailscale groups: `tailscale:tamanu-deploy` and `tailscale:tamanu-engineer`.

### 1.3 pgsnap operator

Runs in `tamanu-seed`. Triggered by creating specific ConfigMaps; produces PostgreSQL snapshots used by the seed-data workflow. Image pinned in the stack config (`pgsnap:imageTag`). Omit the key entirely to skip deploying pgsnap (e.g. demo clusters).

### 1.4 Stack config

Single stack per cluster, e.g. `Pulumi.tamanu-internal-main.yaml`, referencing `bes/k8s-core/tamanu-internal-main`. The only knob that changes day-to-day is `pgsnap:imageTag`.

## 2. `tamanu/on-k8s` — one stack per deployment

The workhorse. Every stack file under `pulumi/tamanu/on-k8s/Pulumi.*.yaml` is one live deployment. Currently ~60 of them: release branches (`release-2-47`), demo builds (`demo-2-44`, `<client>-demo`), epic branches (`epic-invoicing`), feature branches (`feat-*`, `feature-*`), preview branches (`cursor-*`, auto-generated by the editor), and fixes (`fix-*`, `tweak-*`).

### 2.1 Composition

`src/index.ts` builds:

- One `CentralServer` (API, tasks, FHIR refresh/resolver, DB), at `central.{domainBase}`.
- N `FacilityServer`s (API, sync, tasks, DB), at `{facility-name}.{domainBase}`. Default N=2.
- One `WebFrontend` for the patient portal at `portal.{domainBase}`.
- Web frontends for central and every facility (served alongside their API behind the same host).
- Ingress via Envoy Gateway + cert-manager + external-dns (which all live in `k8s-core`/`k8s-essentials`).
- Optional synthetic load-test deployment.

All configuration is computed from a single stack YAML — there's no per-deployment code.

### 2.2 The namespace model — where it gets clever

There's one crucial flag: **`externalNamespace`** (`src/namespace.ts`).

- **`externalNamespace: false`** — Pulumi creates the namespace (`tamanu-{normalizedStack}`), parented to `tamanu-super` via a SubnamespaceAnchor. `pulumi destroy` takes it with.
- **`externalNamespace: true`** — the namespace is already there (created by something *outside* Pulumi — typically a GitHub Actions workflow creating a SubnamespaceAnchor on PR open). Pulumi just references it. When the PR closes, the workflow deletes the anchor, HNC cascades, namespace and everything in it vanishes. Pulumi doesn't race against the teardown.

This is why nearly every `Pulumi.*.yaml` in that directory is a two-line file:

```yaml
config:
  tamanu-on-k8s:externalNamespace: "true"
```

Everything else comes from defaults in `src/config.ts`, and `imageTag` is injected by CI via `pulumi config set` right before `pulumi up`. `Pulumi.main.yaml` is the exception that spells out the full set of defaults explicitly (it's the stable internal staging).

### 2.3 Config reference

Under the `tamanu-on-k8s:` namespace.

#### Required

| Key | Notes |
|---|---|
| `imageTag` | SHA or release tag of the Tamanu container images. All four images (`tamanu-central`, `tamanu-facility`, `tamanu-frontend`, `tamanu-patient-portal`) are pulled from `ghcr.io/beyondessential/` at this tag. Typically `sha-{gitsha}` for previews, `v2.47.x` for releases. |
| `k8s-core` | Always `bes/k8s-core/tamanu-internal-main`. |

#### Common

| Key | Default | Notes |
|---|---|---|
| `namespace` | `tamanu-{normalizedStack}` | Namespace name. Max 56 chars after the `tamanu-` prefix (k8s namespace limit = 63). |
| `externalNamespace` | `false` | See §2.2. Production/preview deployments set this `true`. |
| `domainBase` | `{normalizedStack}.cd.tamanu.app` | Base for all DNS names. Truncated if too long. |
| `facilities` | `2` | Number of facility servers. |
| `facilityNames` | `["facility-1", ..., "facility-N"]` | Override names. Any positions left unset are auto-numbered. Must be unique. |
| `configTemplate` | `basic` | Which template bundle in `tamanu-system` to render. `basic` / `pr` / `rc`. |
| `timezone` | `Pacific/Auckland` | `TZ` env in all containers. |
| `nodeEnv` | `production` | `NODE_ENV`. Staging uses `staging`. |
| `architecture` | `arm64` | `arm64` or `amd64`. Drives pod affinity. |
| `ttlHours` | `0` | Hours the deployment stays up after its latest update — see §2.10. `0` means it is never hibernated. |

#### Replicas

Configurable independently for central and facility, with generic fallbacks.

| Config key | Default | Clamped to |
|---|---|---|
| `centralApiReplicas` / `facilityApiReplicas` / `apiReplicas` | 2 | 0–5 |
| `centralDbReplicas` / `facilityDbReplicas` / `dbReplicas` | 2 | **2–3** |
| `centralTasksReplicas` / `facilityTasksReplicas` / `tasksReplicas` | 1 | 0–1 |
| `centralWebReplicas` / `facilityWebReplicas` / `webReplicas` | 2 | 0–5 |
| `patientPortalReplicas` | 2 | (unclamped) |

The `{central,facility}XxxReplicas` names win over the generic `xxxReplicas`. DB minimum of 2 is enforced — CNPG needs it for failover, so lowering it silently clamps up.

#### Database

| Key | Default | Notes |
|---|---|---|
| `dbStorage` | `5Gi` | PVC size for each CNPG cluster (central and each facility get their own). Format `{n}Gi`. |
| `dbExpose` | `true` | Expose the CNPG primary via a Tailscale LoadBalancer so engineers can `psql` into it directly. |
| `dbBackups` | `false` | Experimental scheduled backups. Don't use yet. |

#### Other

| Key | Default | Notes |
|---|---|---|
| `serviceAccount` | — | Optional service account ARN to attach for AWS access. In `main` it's set to the IPS bucket role — see §5. |
| `syntheticTests` | `false` | If true, deploys an Artillery-based synthetic load tester (1 replica). |
| `ipAllowList` | — | Declared, not wired up yet. |

### 2.4 What a deployment actually looks like

For a default-config deployment in namespace `tamanu-foo`:

```
tamanu-foo
├── central
│   ├── CNPG Cluster (2 replicas, 5Gi)
│   ├── Deployment tamanu-central-api   (replicas=2)
│   ├── Deployment tamanu-central-tasks (replicas=1)
│   ├── Deployment tamanu-central-fhir-refresh
│   ├── Deployment tamanu-central-fhir-resolver
│   ├── Deployment tamanu-central-web   (replicas=2)
│   └── HTTPRoute    → central.foo.cd.tamanu.app
├── facility-1
│   ├── CNPG Cluster (2 replicas, 5Gi)
│   ├── Deployment tamanu-facility-1-api
│   ├── Deployment tamanu-facility-1-tasks
│   ├── Deployment tamanu-facility-1-web
│   └── HTTPRoute    → facility-1.foo.cd.tamanu.app
├── facility-2      (same shape as facility-1)
├── patient-portal
│   ├── Deployment tamanu-patient-portal-web (replicas=2)
│   └── HTTPRoute    → portal.foo.cd.tamanu.app
├── Secrets          (copied from tamanu-system)
└── ServiceAccount   (optional, for IPS)
```

DNS records are materialised by external-dns. TLS is handled automatically by cert-manager via the Gateway API integration. Routes go via a single shared Envoy Gateway (mergeGateways mode) fronted by an NLB — see the Kubernetes doc for details.

### 2.5 Secrets flow

`src/secrets.ts` copies every Secret in `tamanu-system` into the deployment namespace on each `pulumi up`. This means rotating a Mailgun or Bugsnag key in `tamanu-system` and re-running Pulumi picks it up everywhere.

### 2.6 Config templates

The `configTemplate` knob selects which `.njk` bundle in `tamanu-system` to render. Inside the template, Pulumi feeds in: `fqdn`, `timezone`, `instance`, `facilityId`, `deviceId`, CIDR info, and a `randomstring` filter for generating API keys. Output is rendered into a ConfigMap mounted into each container as the Tamanu JSON5 config.

Picking between `basic`, `pr`, `rc`, and `demo` lets you change Tamanu runtime settings across all preview stacks without touching Pulumi code — change the template in `tamanu-system`, then re-run Pulumi on each stack. The `demo` template omits reference data seeding and uses `demos.tamanu.app` as the ingress domain (derived from the cluster's DNS zones, not the template name).

### 2.8 Creating a new deployment

1. Decide whether the namespace is yours (`externalNamespace: false`) or CI-managed (`externalNamespace: true`).
2. Create `Pulumi.{name}.yaml`:
   - For a preview/PR-style deployment: just `externalNamespace: true` and let CI pass `imageTag`.
   - For a persistent demo deployment: set `configTemplate: demo`, `k8s-core`, `facilities`, `imageTag`, and `billing:stage: demo`.
   - For other persistent deployments: also set `configTemplate`, `timezone`, `dbStorage`, and any overrides you need.
3. If CI-managed: open a SubnamespaceAnchor in `tamanu-super` named `tamanu-{name}`.
4. `pulumi up -s {name}`.

### 2.9 Destroying

- `externalNamespace: false`: `pulumi destroy` removes the namespace and everything in it.
- `externalNamespace: true`: `pulumi destroy` removes Pulumi-managed objects, but the namespace survives until the SubnamespaceAnchor is deleted (usually via CI on PR close). Cascading delete will then clean up anything CI or operators left in there.

### 2.10 Time to live and hibernation

These deployments are for testing, so a deployment can be given a time to live with `ttlHours`. Every `pulumi up` sets the expiry that many hours ahead and wakes the deployment. If the expiry passes without another update, the deployment is hibernated. With `ttlHours: 0` (the default) it is never hibernated.

Hibernation has two parts, and both keep the volumes:

1. **Workloads** are held at zero replicas. The hibernation Job sets `downscaler/force-downtime=true` on every Deployment in the namespace, and [`py-kube-downscaler`][kds], running cluster-wide in `k8s-essentials`, scales them to zero.
2. **CNPG `Cluster`s** are hibernated (`cnpg.io/hibernation=on`). The Postgres pods stop and the PVCs stay.

[kds]: https://github.com/caas-team/py-kube-downscaler

Argo CD ignores the replica count and these annotations, so a sync does not undo hibernation. The Argo CD health check reports a hibernated `Cluster` as Healthy, with the message `Hibernated`, and a renderer promotion skips hibernated deployments.

The hibernation Job runs on a 20-minute grid in UTC (minutes 00, 20 and 40), at the first slot at or after the expiry, so it can lag the expiry by up to 20 minutes. A second run follows 10 minutes after the first.

To wake a deployment:

- Run `pulumi up` on its stack. This also sets a new expiry.
- Or run the "Create Job" action on its suspended `wake` CronJob in the Argo CD UI, or `kubectl -n tamanu-<stack> create job --from=cronjob/wake wake-now`. This does not start a new time to live, so the deployment then stays up until the next update.

Wake-up is roughly 30s/Cluster for the Postgres pods plus another 30-60s for app pods to start and warm up. For a tester who needs an environment up for longer, raise `ttlHours` (or set it to `0`) on the relevant stack and `pulumi up`.

The hibernation and wake steps run as the `tamanu-ttl` service account, created by the stub in each namespace that has a time to live, with a namespace-scoped Role permitting `get`, `list` and `patch` on Deployments and `clusters.postgresql.cnpg.io`. The schedule is in `pulumi/tamanu/on-k8s/src/schedule.ts`, and the `wake` CronJob is rendered by the renderer.

## 3. `tamanu/meta` — Tamanu version/meta servers

The meta stack runs two small servers that back the `meta.tamanu.app` / `meta.tamanu.io` endpoints (public version manifest and private orchestration API).

### 3.1 What it deploys

In namespace `tamanu-meta-{stack}`:

- Public server Deployment (2 replicas, Gateway API route).
- Private server Deployment (2 replicas, Tailscale-exposed).
- CNPG PostgreSQL cluster (one, shared between the two servers).
- A CA + DB-migration Job.

Public and private servers run the same image but differ in route/auth config. Private uses mTLS (XFCC client-cert header forwarding, which is why Envoy Gateway was picked — NGINX doesn't do that well).

### 3.2 Config

| Key | Default | Notes |
|---|---|---|
| `imageTag` | **required** | Meta server image. |
| `domains` | `["{stack}.cd.tamanu.app"]` | Public domains this meta server is authoritative for. |
| `replicas` | `2` | Per-server replicas. |
| `dbStorage` | `10Gi` | CNPG PVC. |
| `architecture` | `arm64` | |
| `dbExpose` | `false` in dev, `true` in prod | Tailscale LB over the DB. |
| `publicServerVersionsSecret` | **required** | Pulumi secret with the version JSON payload. |

### 3.3 Stacks

- **`Pulumi.dev.yaml`** — single domain, generic secrets.
- **`Pulumi.prod.yaml`** — multiple domains (`meta.tamanu.app`, `meta.tamanu.io`), 25 Gi storage, production secret.

## 4. `tamanu/ips-infra` + `tamanu/ips` — IPS / S3 publishing

International Patient Summary support. Two stacks.

### 4.1 `ips-infra` — cluster-wide

- Creates the **`public.tamanu.io` S3 bucket** (via CloudFront for edge caching).
- Creates an **EKS IRSA service account** (`ips-bucket`) that pods can use to write to the bucket.
- Creates a **GitHub Actions OIDC role** for the IPS viewer repo to push static content.

Single stack: `Pulumi.main.yaml`.

### 4.2 `ips` — per-deployment

- Creates an **EC2 instance profile** so Linux-variant Tamanu boxes can push to `s3://public.tamanu.io/{stack-name}/*`.
- For K8s-variant deployments, the equivalent is: set `serviceAccount` in `tamanu-on-k8s` to the `ips-bucket` role ARN and the central/facility pods get scoped S3 write access under the deployment's prefix.

Single stack: `Pulumi.main.yaml`.

## 5. End-to-end request flow

For a request to `central.foo.cd.tamanu.app`:

1. Route53 has an A/AAAA record (created by external-dns, watching the HTTPRoute) pointing at the shared Envoy NLB.
2. NLB terminates TCP/UDP on 443, preserves client IP, forwards to Envoy proxy pods on ingress nodes.
3. Envoy matches the HTTPRoute to the `central` Service in `tamanu-foo`, terminates TLS using a cert-manager-issued Let's Encrypt cert, routes `/api` to the central API Service, `/v1` to the legacy API endpoint, and `/` to the central web Service.
4. Central API pods talk to their CNPG cluster over the pod network. The DB cluster's primary is exposed over Tailscale if `dbExpose: true` — used by engineers for direct `psql`, not by the app.
5. Facility servers at `facility-1.foo.cd.tamanu.app` etc. follow the same pattern but also hold a sync channel to `https://central.foo.cd.tamanu.app`.

## 6. Quick reference

| Concern | Where |
|---|---|
| Shared templates & secrets | `tamanu/k8s-infra` → `tamanu-system` ns |
| Deployment RBAC | `tamanu/k8s-infra` → `tamanu-deploy` / `tamanu-engineer` ClusterRoles, HNC-propagated |
| Per-deployment namespace anchor | CI creates SubnamespaceAnchor in `tamanu-super` |
| Application stack | `tamanu/on-k8s` |
| Ingress machinery | Envoy Gateway (shared, cluster-wide) |
| DB | CNPG Cluster per central + per facility |
| DNS | external-dns watching Gateway HTTPRoutes |
| TLS | cert-manager with LE/DNS-01 |
| Direct DB access | Tailscale LB over CNPG primary, when `dbExpose: true` |
| Time-to-live hibernation | py-kube-downscaler (cluster-wide) + CNPG hibernation, run by the stub's hibernation Jobs when `ttlHours` is set |
| Version/meta site | `tamanu/meta` |
| IPS S3 publishing | `tamanu/ips-infra` + `tamanu/ips`, SA wired via `serviceAccount` |
| PR preview lifecycle | GitHub Actions creates anchor + sets `imageTag`; `pulumi up -s {name}`; on close, CI deletes the anchor and HNC cascades. |

See `docs/kubernetes.md` for the cluster layer this all sits on, and `docs/tamanu-on-linux.md` for the non-K8s variant of Tamanu.
